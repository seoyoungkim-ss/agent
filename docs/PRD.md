# 사내 카페테리아 운영 관리 홈페이지 기획서

## 0. 문서 정보
- 작성일: 2026-07-27
- 상태: 초안 (Draft) — 요구사항 정리 단계
- 목적: 사내 카페테리아(구내식당) 운영 데이터를 수집·분석하여 리더 보고, 협력사 메뉴 컨펌, 운영 개선, 혼잡도 관리에 활용할 수 있는 내부 홈페이지 구축

## 1. 프로젝트 개요

### 1.1 배경
- 카페테리아 취식 로그와 주간 식단표를 기반으로 식수 예측, 만족도 분석, 혼잡도 관리를 자동화한다.
- 평일과 주말·공휴일의 식수 패턴 차이가 크므로, 모든 분석/시뮬레이션 화면에서 **평일 / 주말+공휴일** 구분을 공통 필터로 제공한다.

### 1.2 배포 방식
- 코드는 사외 Git(GitHub 등)에 올려 관리하고, 사내망에서는 해당 저장소를 다운로드(clone/pull)하여 폐쇄망 서버에 빌드·배포한다.
- 즉, **개발/버전관리는 사외 Git, 실행/데이터 적재는 사내망**으로 분리되는 구조.
- 이 특성상 다음을 설계에 반영해야 한다.
  - 저장소에는 소스코드/스키마/설정 템플릿만 포함하고, 실제 취식 데이터(개인정보 포함 가능성 있는 사번 등)는 **절대 커밋하지 않는다.** (`.gitignore`로 데이터/DB 파일 제외)
  - 사내 LLM API 등 사내 전용 리소스에 대한 연동 정보는 환경변수/설정 파일로 분리하여 외부에 노출되지 않게 한다.
  - 사내망 배포 스크립트(설치/마이그레이션/시드)를 문서화하여, 다운로드 후 바로 구동 가능하게 한다.
- 저장소에는 배포 대상이 서로 다른 두 컴포넌트가 함께 포함된다 (상세: 9.2, 9.5).
  1. **웹 대시보드**(FastAPI + React + PostgreSQL): 사내 Linux 서버에서 Docker Compose로 구동
  2. **데이터 수집 도구**(`ingestion-tool/`): 나스카(DRM) 때문에 원본 취식 로그(CSV)와 주간 식단표(xlsx)를 Excel로 직접 열어야 하므로, Excel이 설치된 **운영자 Windows PC에서 별도로 실행**하는 도구로 분리

### 1.3 핵심 컨셉
1. **홈 화면(대시보드)**: 실시간/주간 운영 현황을 리더 보고 및 협력사 메뉴 컨펌 용도로 제공
2. **분석 탭**: 사용자 분석(입맛/식수) + 코너별 분석(만족도/서브 속도/코어층)
3. **시뮬레이션 탭**: 외부 변수(날씨/신메뉴/행사) 기반 식수 시뮬레이션, 코너 혼잡도 분산 시뮬레이션
4. **Agent 채팅**: 사내 LLM API 연동, 자연어로 대시보드/분석 결과 질의

## 2. 사용 가능한 데이터

### 2.1 `mealdata.csv` (취식 로그)
| 컬럼 | 설명 | 비고 |
|---|---|---|
| 취식일자 | 취식 일시 (초 단위 타임스탬프로 추정) | 피크타임(11:40~12:00) 분석 시 초 단위 태깅 활용 |
| 사내 ID | 사번 | 개인 취식 이력 추적, 입맛 프로파일링 키 |
| 식사구분 | 조식/중식/석식 | |
| 코너 | 취식한 코너명 | 7개 코너 + 그린미트(다이어트식, 별도 분류) |
| 맛평가 | 개선/보통/맛남 (3단계) | 만족도 지표의 기본 단위. **점수 환산: 맛남=5점 / 보통=3점 / 개선=1점 (5점 만점 척도)**. 표본 수 보정 방법은 6.3 참조 |
| 주관식의견 | 자유 텍스트 | 있을 수도, 없을 수도 있음 → VOE 클러스터링 원천 데이터 |

> ⚠️ 사번(사내 ID)은 개인식별 가능 정보이므로, 분석 시에는 가명처리/집계 단위로 다루고 원본 접근 권한을 제한한다.

### 2.2 주간 식단표
- 급식표 형태의 병합 셀 포함 스프레드시트.
- 구조:
  - 1번째 컬럼: 조식/중식/석식 구분
  - 2번째 컬럼: 코너명
  - 3번째 컬럼부터: 월~일 요일별 메뉴 (메인메뉴 + 부찬이 섞여 있고 경계가 모호함)
- **파싱 시 주의사항**
  - 병합 셀은 위/왼쪽 값으로 forward-fill 처리 필요 (조/중/석식, 코너명 컬럼)
  - 메인메뉴 vs 부찬 구분 규칙 정의 필요 (예: 줄바꿈/구분자 기준 1번째 항목=메인, 이후=부찬으로 우선 가정 후 검증, 혹은 별도 메뉴 마스터 테이블과 매칭하여 카테고리 태깅)
  - 향후 메뉴명 정규화(동일 메뉴의 표기 편차 통일)를 위한 메뉴 마스터 테이블이 필요함

## 3. 공통 요구사항

### 3.1 평일 / 주말+공휴일 토글
- 홈 화면, 분석 탭, 시뮬레이션 탭의 **모든 화면**에서 조회 기준을 아래 중 선택 가능해야 한다.
  - 평일
  - 주말 + 공휴일
  - (선택) 전체
- 휴일 판단 로직에 아래를 모두 포함한다.
  - 법정 공휴일 (설날/추석 연휴, 삼일절, 어린이날, 광복절 등)
  - **대체공휴일**
  - **근로자의 날(5/1)** — 법정 공휴일은 아니지만 식수 패턴이 주말과 유사하므로 휴일로 분류
  - (선택) 회사 자체 휴무일/창립기념일 등 커스텀 휴일 — 관리자가 수동 등록 가능하도록 확장

### 3.2 휴일 마스터 데이터 관리
- 공휴일 데이터는 매년 갱신이 필요하므로, DB에 `holiday_calendar` 테이블로 별도 관리한다.
- 최초 구축 시 공공데이터포털 특일 정보 API 또는 수동 입력으로 시딩하고, 연 1회(또는 자동 배치) 갱신한다.
- 관리자 화면(또는 시드 스크립트)에서 근로자의 날, 대체공휴일, 회사 자체 휴무일을 수동으로 추가/수정할 수 있게 한다.

## 4. 데이터베이스 설계 (안)

데이터는 앞으로 계속 누적되는 구조이므로, 원본 로그성 데이터와 집계/파생 데이터를 분리해서 설계한다.

### 4.1 원본/기준 테이블
- **`meal_log`** (취식 로그, append-only)
  - `id`, `eaten_at`(초단위 timestamp), `employee_id`, `meal_type`(조/중/석식), `corner_id`, `taste_score`(개선/보통/맛남), `comment`(nullable), `menu_snapshot_id`(해당 일자 실제 제공 메뉴 FK, 선택), `loaded_at`
- **`employee_master`**
  - `employee_id`, `division`(본사/계열사/기타), `department`, `join_date` 등 (개인 민감정보 최소화)
- **`corner_master`**
  - `corner_id`, `corner_name`, `is_diet_corner`(그린미트 여부), `avg_capacity`(참고용) 등
- **`menu_master`**
  - `menu_id`, `menu_name`(정규화명), `category`(메인/부찬/국 등), `food_vector`(단백질/탄수/매운맛 등 특성 벡터 or 태그 배열)
- **`weekly_menu_plan`** (주간 식단표 파싱 결과)
  - `plan_date`, `meal_type`, `corner_id`, `menu_id`, `menu_role`(메인/부찬), `is_new_menu`, `source_row_raw`(원본 셀 원문, 파싱 검증용)
- **`holiday_calendar`**
  - `calendar_date`, `holiday_type`(법정공휴일/대체공휴일/근로자의날/회사자체휴무), `holiday_name`, `is_weekend`

### 4.2 집계/파생 테이블 (배치로 매일 갱신)
- **`daily_corner_stats`**: 일자·코너·식사구분별 이용자수, 평균 만족도, 피크타임 처리량(초단위 로그 → 분당 서브 건수)
- **`daily_division_stats`**: 일자·구분(본사/계열사/기타)·식사구분별 식수
- **`employee_taste_profile`**: 사번별 메뉴/카테고리 선호 벡터 (배치로 주기 갱신)
- **`monthly_voe_cluster`**: 월별 주관식의견 클러스터링 결과(사내 LLM 임베딩/요약 활용), 클러스터 라벨, 대표 코멘트, 건수
- **`congestion_forecast`**: 코너/시간대별 혼잡도 예측 결과 (시뮬레이션 탭과 공유)
- **`menu_performance_stats`**: 기간(월별/6개월 롤링)·메뉴별 등장횟수, 총 식수, 평가건수, 평가율, 원점수(raw_score), 표본 보정 점수(adjusted_score), 식수 점유율(share) 추이, 4분면 라벨(인기메뉴/숨은강자/개선시급/퇴출후보) — 상세 산출식은 6.3 참조

### 4.3 설계 원칙
- 원본 로그(`meal_log`, `weekly_menu_plan`)는 수정하지 않고 계속 append하며, 정정이 필요하면 이력(버전) 컬럼으로 관리한다.
- 집계 테이블은 배치(예: 매일 새벽) 재계산하여 대시보드 응답 속도를 확보한다.
- 개인정보(사번) 접근은 분석/집계 파이프라인 내부로 제한하고, 화면 노출 시에는 집계 단위(부서/구분/클러스터)로만 제공한다.

## 5. 홈 화면 (대시보드)

### 5.1 목적/사용자
1. **파트장/그룹장 등 리더 보고용** — 현황을 엑셀 또는 이미지로 다운로드 가능해야 함
2. **식당 운영자** — 2주 전, 2주 뒤 주간 식단표를 협력사와 컨펌하는 회의 자료로 활용

### 5.2 구성 요소
- 실시간 주간 현황 (금주 일별 식수 추이, 평일/휴일 필터 적용)
- 이번 주 예상 혼잡도 (코너/시간대별)
- 주간 만족도 (전체 평균, 전주 대비 증감)
- 이번 주 메뉴별 과거 이력 — 동일/유사 메뉴가 이전에 제공됐을 때의 만족도 점수와 대표 코멘트를 함께 노출 (협력사 컨펌 시 "이 메뉴는 지난번 평가가 안 좋았다" 같은 근거 제공)
- 월간 VOE 클러스터링 (사내 LLM API로 주관식 의견을 주제별로 군집화, 대표 이슈/키워드 카드로 노출)
- **다운로드 기능**: 화면 스냅샷(이미지) 또는 엑셀(원자료+요약 시트) export

### 5.3 추가 제안 (운영관리 관점)
- **2주 뒤 식단 컨펌 전용 위젯**: 협력사가 제안한 메뉴안과, 동일 메뉴의 과거 만족도/코멘트, 예상 혼잡도(신메뉴/반복도 기반)를 나란히 비교하는 보드 → 회의 중 바로 승인/반려/코멘트 입력
- **이슈 알림 배너**: 특정 코너 만족도 급락, 특정 메뉴 부정 코멘트 급증 등 이상 신호 자동 감지 및 표시
- **신메뉴 트래커**: 최근 신메뉴 목록과 초기 반응(맛평가 분포)
- **재고/발주 참고 지표**(연동 데이터 있을 경우 확장): 예상 식수 기반 필요 수량 가이드
- **주간 리포트 자동 생성**: 매주 월요일 기준 전주 요약을 PDF/엑셀로 자동 생성해 리더에게 배포(추후 메일 연동 확장 여지)

## 6. 분석 탭

### 6.1 사용자 분석
- **식수 집계**: 본사/계열사/기타 구분 × 일간/주간/월간, 평일/휴일 필터 적용
- **개인 입맛 분석 (Taste Profiling)**
  - 사번 단위로 선택 메뉴 이력을 벡터화하여, 메뉴 선택에 일관된 성향이 있는지 분석
    - 예: 떡볶이 선호자가 짜장면도 자주 선택하는지(분식/매콤 카테고리 선호), 단백질류 선호자가 대체 메뉴 부재 시 고단백 메뉴를 선택하는지
  - **메인메뉴 음식벡터**(`menu_master.food_vector`: 매운맛/단백질/탄수/국물 유무 등 특성) × **개인 선호 벡터**를 결합한 하이브리드 추천/예측 모델
  - 활용처
    - 식수 예측 정확도 개선 (개인 선호 반영한 코너별 수요 예측)
    - 만족도 개선 (선호 클러스터별 메뉴 구성 제안)

### 6.2 코너별 분석
- 대상: 7개 코너 (그린미트는 다이어트식 특성상 별도 카테고리로 분리하여 분석)
- 동일 메뉴가 2~3개 코너에서 동시 제공되는 경우를 고려하여, **메뉴 단위**와 **코너 단위** 분석을 모두 지원 (메뉴-코너 매핑 다대다 처리)
- 분석 항목
  - 코너별 이용자 수 (일/주/월)
  - 코너별 만족도
  - 코너별 식수 예측
  - 코너별 코어층 분석 (해당 코너를 반복적으로 선택하는 사번 그룹의 특성)
  - **서브 속도(처리량) 분석**: 피크타임(11:40~12:00) 구간의 취식 로그를 초 단위로 집계 → 분당 태깅 건수 평균을 코너별 서빙 속도 지표로 산출 (병목 코너 파악에 활용)

### 6.3 메뉴별 성과 분석 (만족도 스코어링 · 빈도 · 하락 원인 · 4분면)
취식 데이터는 **6개월 누적**이며, 동일 메뉴가 기간 내 여러 번 반복 제공된다. 단순 평균 만족도만으로는 "평가 몇 건 안 받고 우연히 높게 나온 메뉴"가 과대평가될 위험이 있고, "식수가 줄었다"는 현상만으로는 그 메뉴 자체가 별로여서인지 그날 전체 식수가 원래 적었는지 구분할 수 없다. 이를 보완하기 위해 아래 지표를 메뉴별로 산출한다.

#### 6.3.1 만족도 점수화 및 표본 수 보정
- **점수 환산**: 맛남=5점, 보통=3점, 개선=1점 → 평가 건의 평균이 **원점수(raw_score, 5점 만점)**
- **표본 수 보정(베이지안 축소, Bayesian shrinkage)**: 평가 건수(n)가 적은 메뉴가 원점수만으로 상위에 노출되지 않도록, 전체(또는 동일 코너/식사구분) 평균으로 점수를 당겨서 보정한다.
  - `adjusted_score = (n / (n + m)) × raw_score + (m / (n + m)) × global_avg_score`
    - `n`: 해당 메뉴의 평가 건수
    - `m`: 신뢰 기준 평가건수(보정 강도 상수, 예: 20~30건 — 데이터 분포 보고 튜닝)
    - `global_avg_score`: 같은 기간·같은 코너/식사구분의 전체 평균 만족도
  - n이 작을수록 adjusted_score는 global_avg_score 쪽으로 수렴 → "평가 몇 개로 반짝 고득점"을 방지
- **화면 표기 원칙**: 만족도는 항상 `adjusted_score (n=평가건수)` 형태로 함께 노출하고, n이 임계치(예: 10건) 미만이면 "표본 부족" 배지를 붙여 순위/랭킹류 화면에서 오해를 방지한다.

#### 6.3.2 빈도 지표 (6개월 누적 기준)
메뉴별로 만족도와 별도로 아래 빈도 지표를 함께 제공한다.
- **등장 횟수**: 6개월 내 해당 메뉴가 제공된 일수
- **등장 주기**: 평균 재등장 간격(일), 최근 등장일
- **총 식수**: 해당 메뉴를 선택한 누적 인원 수
- **평가율**: 평가건수(n) / 총 식수 — 평가율 자체도 메뉴별 관심도/이슈 정도를 보여주는 참고 지표
- 목적: "자주 나오는데 평가가 적다", "가끔 나오는데 평가가 몰린다" 같은 패턴을 만족도 해석과 함께 볼 수 있게 함

#### 6.3.3 식수 하락 원인 분해 (만족도 vs 전체 트래픽)
메뉴별 식수가 하락할 때, **만족도 저하 때문인지 / 그날 전체 식수 자체가 줄어서인지**를 구분하기 위해 절대 지표와 상대 지표를 함께 본다.
- **절대 식수(headcount)**: 해당 메뉴를 선택한 인원 수 (기간별 추이)
- **점유율(share)**: `해당 메뉴 식수 ÷ 같은 날·같은 식사구분(또는 코너) 전체 식수` — 전체 트래픽 변동을 통제한 지표로, 전체 식수가 줄어도 점유율이 유지되면 그 메뉴 자체의 인기는 유지되고 있다는 뜻
- **만족도 추이**: adjusted_score의 기간별 이동평균(예: 최근 3회 제공분 평균)
- **원인 진단 로직(단순 매트릭스)**
  | 점유율 추이 | 만족도 추이 | 해석 |
  |---|---|---|
  | 하락 | 하락 | 메뉴 자체 만족도 이슈 → 레시피/조합 개선 필요 |
  | 하락 | 유지/상승 | 만족도는 괜찮은데 선택이 줄어듦 → 경쟁 메뉴 등장, 동시간대 대체재 증가 등 확인 필요 |
  | 유지/상승 | 유지/상승 | 전체 식수 하락은 계절·공휴일 등 외부 요인일 가능성 높음(메뉴 이슈 아님) |
  | 유지/상승 | 하락 | 만족도는 떨어졌지만 대안이 없어 계속 선택되는 상태 → 잠재 이탈 위험, 우선 개선 대상 |
  - 참고 지표로 회귀 기반 기여도 분해(`Δheadcount ≈ β1·Δ전체식수 + β2·Δ만족도`)도 확장 옵션으로 고려 가능

#### 6.3.4 메뉴 4분면 매트릭스 (인기메뉴 / 숨은강자 / 개선시급 / 퇴출후보)
- **X축(수요)**: 등장 빈도 또는 1회 제공당 평균 식수(6.3.2)
- **Y축(만족도)**: 표본 보정된 `adjusted_score`(6.3.1)
- **4분면 정의**

  | | 만족도 High | 만족도 Low |
  |---|---|---|
  | **수요 High** | 인기메뉴 — 자주 나오고 평가도 좋음, 유지 | 개선시급 — 자주 나오는데 평가가 나쁨, 개선 우선순위 최상위 |
  | **수요 Low** | 숨은강자 — 잘 안 나오지만 나오면 평가 좋음, 노출 빈도 확대 후보 | 퇴출후보 — 잘 안 나오고 평가도 나쁨, 메뉴 축소/교체 후보 |

- 축 기준선은 전체 메뉴의 중앙값(median) 또는 관리자가 조정 가능한 임계값으로 설정
- 평가건수(n)가 임계치 미만인 표본 부족 메뉴는 4분면에서 별도 색상(회색 등)으로 구분 표시하여, 우연한 고/저 점수로 사분면 판정이 왜곡되지 않도록 한다
- 이 4분면 결과는 7.2(코너별 주간 메뉴 조합 추천)에서 **퇴출후보/개선시급 메뉴의 교체 시뮬레이션** 입력으로 연계 활용한다

## 7. 시뮬레이션 탭

### 7.1 조건부 메뉴 시뮬레이션
- 입력 변수: 날씨(맑음/비/폭염/한파 등), 신메뉴 등장 여부, 사내 행사 유무 등
- 출력: 해당 조건 하에서의 예상 식수/코너별 수요 변화, 참고할 과거 유사 조건 사례

### 7.2 코너별 주간 메뉴 조합 추천 / 혼잡도 분산 시뮬레이션
- 혼잡이 몰릴 것으로 예측되는 코너·시간대를 미리 탐지
- "이 코너 또는 다른 코너의 메뉴를 바꾸면 혼잡도가 어떻게 변하는지"를 What-if 방식으로 시뮬레이션
  - 예: A코너에 인기 메뉴가 몰릴 것으로 예측될 때, B코너 메뉴를 조정하면 분산 효과가 있는지 시뮬레이션
- 6.1의 개인 선호 벡터 + 6.2의 코너별 서브 속도를 결합하여, 특정 메뉴 조합에 따른 예상 혼잡도(대기시간)까지 추정
- 6.3의 메뉴 4분면 결과(특히 개선시급/퇴출후보)를 교체 후보 풀로 활용하여, "이 메뉴를 숨은강자 메뉴로 교체하면 혼잡도/만족도가 어떻게 변하는지" 시뮬레이션

## 9. 기술 스택 (확정)

### 9.1 결정 배경
- 사내망: 완전 폐쇄망이 아니라 **사내 미러/프록시로 pip/npm 설치 가능**
- 개발·유지보수 인력: **1인 또는 소수의 풀스택 담당** → 운영 부담이 큰 구성요소(별도 메시지 큐, 마이크로서비스, 별도 벡터DB 등)는 배제하고 구조를 최대한 단순화
- DB: 사내 표준인 **PostgreSQL** 채택

### 9.2 데이터 수집(Ingestion) 계층 — DRM(나스카) 대응
사내 보안 프로그램(나스카 등 DRM)이 걸려 있어 `mealdata.csv`와 주간 식단표(xlsx) **모두** 원문 파일을 직접 여는 방식(pandas.read_csv, openpyxl 등)으로는 내용을 읽을 수 없다. DRM은 실제 승인된 애플리케이션(Excel 등)이 파일을 열 때만 자체 복호화하는 구조이기 때문에, 파싱은 **컨테이너화된 Linux 백엔드가 아니라 Excel이 실제 설치된 Windows 환경에서** 이뤄져야 한다. 이 요구사항으로 인해 수집 파이프라인은 웹 대시보드와 물리적으로 분리된 별도 구성요소로 설계한다.

| 항목 | 결정 | 비고 |
|---|---|---|
| 실행 위치 | **운영자 PC (Windows, Excel + 나스카 클라이언트 설치됨)** | 상시 가동 서버가 없으므로 자동 스케줄링이 아닌 **수동 실행형** 도구로 시작 |
| 실행 트리거 | 운영자가 새 취식 로그/주간 식단표 파일을 받을 때마다 직접 실행 | 정기 실행을 놓치면 데이터 공백이 생길 수 있으므로, 운영 체크리스트(예: "매주 O요일 실행")로 보완 필요 |
| 라이브러리 | **xlwings** (+ pywin32) | 실제 Excel 인스턴스를 열어 나스카가 복호화한 값을 COM으로 읽어옴. `mealdata.csv`도 DRM 대상이므로 Excel로 열어 읽는 방식(`wb = xw.Book(path)`)을 동일하게 적용 |
| 파싱 로직 위치 | 이 로컬 도구 안에서 병합 셀 forward-fill, 조/중/석식·코너명 채우기, 메인/부찬 분리, 요일별 컬럼 매핑까지 전부 처리 | 4.1의 `weekly_menu_plan`/`meal_log` 스키마에 맞춰 정제된 행 단위 데이터로 변환 |
| 서버 전송 | 정제된 구조화 데이터(원문 셀 값이 아니라 파싱 결과)만 사내망 HTTPS로 백엔드의 `/ingest/meal-log`, `/ingest/weekly-menu` API에 POST | 복호화된 원본 파일 자체는 서버로 옮기지 않고, 로컬에서 파싱까지 끝낸 결과만 전송 → DRM 정책 위반 소지 최소화 (사내 보안팀 확인 권장) |
| 확인 UX | 전송 전 파싱 결과 미리보기(행 수, 이상치/빈 셀 경고, 신규 메뉴 여부)를 화면에 보여주고 운영자가 확인 후 전송 | 병합 셀·메인/부찬 경계 오파싱 위험이 있으므로 전량 자동 전송보다 확인 단계를 둠 |
| 배포 형태 | 같은 저장소의 `ingestion-tool/` 서브폴더에 소스 포함, **PyInstaller로 단일 실행 파일(.exe)** 빌드해 운영자 PC에 배포 | 운영자 PC에 Python 설치를 요구하지 않기 위함 |
| 인증 | 백엔드 API 호출 시 단순 사내 API 키(고정 토큰) 사용 | 사내망 내부 통신이므로 과도한 인증 체계는 배제, 다만 HTTPS는 유지 |

> ⚠️ 이 구조 때문에 웹 대시보드(9.4 배포)의 "Docker Compose로 clone 후 바로 구동"은 **대시보드 자체에만 해당**하고, 데이터 수집은 별도의 Windows 로컬 실행 도구로 분리된다. 두 컴포넌트는 같은 Git 저장소에 포함하되 배포 대상(Linux 서버 vs 운영자 Windows PC)이 다르다는 점을 문서화해야 한다.

### 9.3 백엔드
| 영역 | 선택 | 이유 |
|---|---|---|
| 언어/프레임워크 | Python 3.11+ / FastAPI | 데이터 분석(pandas, scikit-learn 등)과 API 서버를 같은 언어로 유지 → 1인 개발 시 컨텍스트 스위칭 최소화. `ingestion-tool`과도 Python으로 통일되어 파싱 로직 재사용 용이 |
| ORM/마이그레이션 | SQLAlchemy + Alembic | 4장 DB 설계가 계속 확장될 것을 고려해 스키마 변경 이력 관리 |
| DB | PostgreSQL + `pgvector` 확장 | 사내 표준 DB. 메뉴 `food_vector`, 사번 취향 벡터, VOE 임베딩을 별도 벡터DB 없이 pgvector로 저장·유사도 검색 |
| 데이터 수신 | FastAPI `/ingest/*` API가 9.2 로컬 도구로부터 정제된 데이터를 받아 적재 | 백엔드는 원본 파일을 직접 파싱하지 않음(DRM으로 불가) — 이미 정제된 데이터를 검증 후 저장하는 역할만 수행 |
| 분석/모델링 | scikit-learn(클러스터링·유사도), lightgbm(식수 예측 회귀) | 6개월 치 정형 데이터 규모에 적합하고 딥러닝 대비 운영 부담이 낮음 |
| 배치/스케줄러 | APScheduler (앱 프로세스 내 크론) | 이미 DB에 적재된 데이터를 대상으로 일 배치(집계 테이블 갱신)와 월 배치(VOE 클러스터링)를 수행 → 1인 운영에 적합. 데이터/트래픽이 커지면 Celery 전환 검토 |
| 엑셀/이미지 export | xlsxwriter(엑셀), Playwright headless(이미지 스냅샷) | 리더 보고용 다운로드 요구사항(5.2) 충족 |
| 사내 LLM 연동 | 사내 LLM API를 HTTP 클라이언트로 호출, 엔드포인트/키는 `.env` | Agent 채팅과 월간 VOE 클러스터링(임베딩+요약)에 공용 사용 |

| 프레임워크 | React + TypeScript + Vite | 4탭 구조, 4분면 인터랙티브 차트, 채팅 스트리밍 UI 등 커스텀 인터랙션이 많아 Streamlit/Dash보다 자유도가 필요 |
| UI 컴포넌트 | shadcn/ui | 커스터마이징이 쉬워 별도 디자인 시스템 구축 부담이 적음 |
| 차트 | ECharts | 4분면 산점도(6.3.4), 피크타임 서브속도 히트맵(6.2), 추이선 등 다양한 차트 요구를 하나의 라이브러리로 커버 |
| 서버 상태 관리 | TanStack Query | Redux 등 무거운 상태관리 없이 API 데이터 패칭·캐싱만으로 충분 |
| 채팅 스트리밍 | SSE (Server-Sent Events) | 사내 LLM 응답 실시간 스트리밍, WebSocket 대비 구현·운영이 단순 |

### 9.5 배포/인프라
- **웹 대시보드 컨테이너화**: Docker Compose로 `app`(FastAPI + 빌드된 React 정적 파일 서빙) + `db`(PostgreSQL) 2개 서비스로 구성 → 사내망에서 clone 후 `docker compose up` 한 번으로 구동하는 것을 목표로 함
- **데이터 수집 도구 배포**: `ingestion-tool/`은 컨테이너화 대상이 아니라 PyInstaller `.exe`로 빌드해 운영자 Windows PC에 별도 설치/배포 (9.2 참조)
- **패키지 설치**: 사내 pip/npm 미러(프록시)를 `pip.conf`/`.npmrc`에 설정해 빌드 시 사용. 향후 완전 폐쇄망으로 전환될 가능성에 대비해 `requirements.txt`/`package-lock.json` 버전을 고정 관리(오프라인 wheel 번들링 전환이 쉽도록)
- **환경변수 관리**: `.env.example`을 저장소에 포함하고 실제 `.env`(DB 접속정보, 사내 LLM API 키, `/ingest` API 토큰 등)는 `.gitignore` 처리, 사내 배포 시에만 값 채움
- **DB 마이그레이션 배포**: Alembic 마이그레이션을 배포 스크립트에 포함해 버전 업 시 자동 적용
- **권한 관리**: 리더/운영자/일반 사용자 등 역할별 화면 접근 및 다운로드 권한 분리 필요(향후 정의)

### 9.6 검토했으나 채택하지 않은 대안
- **백엔드에서 openpyxl/pandas로 원본 파일 직접 파싱**: 나스카 DRM 때문에 원문 파일 자체를 읽을 수 없어 배제 (9.2 참조)
- **Streamlit/Dash 단일 Python 앱**: 초기 MVP 속도는 빠르지만 4분면 인터랙션, 채팅 스트리밍, 리더용 정교한 다운로드 UX 등 커스텀 요구가 많아 장기적으로 제약이 큼 → 제외 (단, 분석 탭 일부를 먼저 빠르게 검증하려는 목적이라면 프로토타입 용도로는 선택 가능)
- **Celery + Redis 비동기 작업 큐**: 배치 작업 빈도(일 1회 집계, 월 1회 VOE 클러스터링) 대비 운영 인프라 부담이 커서 제외, APScheduler로 충분
- **별도 벡터 DB(Milvus/Pinecone 등)**: PostgreSQL `pgvector` 확장으로 충분히 커버돼 인프라 추가 없이 진행
